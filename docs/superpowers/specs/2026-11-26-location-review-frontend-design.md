# 地址人工复核 前端设计

## 背景与目的

后端（`docs/superpowers/specs/2026-11-25-location-review-design.md`及对应实现计划）已经完整落地并在生产端真实验证通过：8个API接口（队列列表/详情/生成候选/人工决策/解锁/新建地点/合并分组/一致率统计），白名单token鉴权。目前只能用curl调，没有界面。

用户明确表态："重型前端，尽量好看些，不怕重"——这是未来大前端里的第一个分支功能，要按长期维护的标准做，不是糊一个临时页面。本次范围：把后端已有的全部能力（不只是"看图做决策"这一核心流程，还包括地点/分组管理、一致率看板）都做出界面。

## 目标 / 非目标 / 反目标

**目标**
- 复核队列：按状态筛选、分页浏览待审/已审条目。
- 核心复核界面：当前视频截图 vs 候选地点参考图并排对比，下方展示GPS距离+视觉比对指标（内点数/内点率/是否自动通过）+LLM判断（影子模式，仅展示不采信），人工点击"确认同一地点/不是这个候选/新地点"三种决策，以及对已锁定视频的"解锁"操作。
- 地点管理：新建地点（填城市+site前缀）。
- 分组管理：选择多个地点合并成一个`location_group`。
- 一致率看板：展示LLM与人工决策的一致率统计（`total`/`agreed`/`disagreed`/`ready_for_automation`），纯展示，不触发任何自动化。
- 鉴权：输入token（CLI脚本发的）登录，本地存储，后续请求都带上。
- **"文件夹审查"面板**：输入一个文件夹路径（session文件夹，如`.../panshiroad_city_m3e_120m_someone_20261020`），看这个文件夹下全部视频，标出哪些已经有`location_id`、哪些没有（可能是自动聚类判定"飞行不稳定"或者GPS漂移太大被排除）——人工凭肉眼判断"这些没被收进去的，是不是算法筛得太狠了"，选中某条视频手动触发生成复核候选（`POST /queue/generate`）。

**非目标**
- 不做账号密码登录/用户注册——后端就没有这个系统，前端也不假装有。
- 不做token的前端管理界面（发token/撤销token还是走CLI脚本，不在这次前端范围）。
- 不改动后端已有的任何业务逻辑——前端纯粹是现有API的消费者，顶多因为前端需要而给后端加一两个**只读**字段（见下面"需要的后端小补丁"）。

**反目标（即使做出来也算失败）**
- 为了"重型好看"而牺牲核心流程的操作效率——人工复核是要高频重复操作的工作流，不是只看一次的展示页，按钮/快捷键这些效率细节不能被视觉设计牺牲掉。
- 把LLM的判断做得比人工决策更显眼/更有分量——LLM在本阶段只是影子观察者，UI上的视觉权重必须明显弱于人工决策区域，不能让复核员下意识被LLM结果带偏判断。

## 约束

- 后端鉴权是纯Bearer token（无session/无cookie），前端是纯SPA，不需要考虑SSR/CSRF。
- 后端目前完全没有CORS配置——前端如果跟后端不同源部署，需要后端加CORS中间件（这个小改动包含在这次一起做，不单独立项）。
- 多帧扩展：这次只提一帧，但接口与组件现在就按"一组图片"设计（见下方approaches）。

## 已决定的方案（Approaches）

### 核心对比面板布局
考虑过三种：
- **A. 并排+底部指标条**：两张图左右等大并排，下面一行文字列出全部指标。信息密度高，判断"是不是同一地点"时两张图地位对等，最直白。
- B. 滑块叠加对比：适合找细微差异，但两张图视角/构图通常不同，叠加对比意义不大。
- C. 主图+缩略图+徽章：候选图被弱化成缩略图，不适合"两者对等判断"的场景。

**用户已选定A**（浏览器交互确认）。

### 多帧扩展预留
后端这次只提一帧（`extract_frame`只提第一帧），但**API返回层面现在就把`screenshot_path`包成`screenshot_paths`数组**（哪怕现在永远只有1个元素），前端的图片展示组件直接设计成"横向画廊"组件（现在只渲染1张）。以后后端真的支持多帧时，数组里多塞路径、画廊组件自动适配，前端和接口契约都不用改。这是本次要做的一个小后端改动（序列化层面，不改数据库/不改提帧逻辑），详见下方"需要的后端小补丁"。

### 技术栈
React + TypeScript + Vite——跟`extern/AD_pipeline_1`新版workbench-ui保持一致的技术选型（用户没有表达异议，按"outcome决定how"的原则由我决定）。

### 鉴权方式
一个简单的"粘贴token"登录页：用户从CLI脚本拿到明文token，贴进输入框，存到`localStorage`，之后所有请求都在`Authorization: Bearer`里带上。没有后端session，刷新页面靠localStorage里的token免登录；token失效(401)时跳回登录页重新贴。

### 页面结构
左侧边栏导航，五个一级入口（不是视觉决策，常规管理后台布局，未单独展示给用户挑选）：
- **队列**（默认首页）：复核队列列表+详情面板（核心流程）；队列列表每条item若对应视频已`location_confirmed`（被其它候选条目决策锁定），灰显/可折叠，不当成待办
- **文件夹审查**：输入文件夹路径，看这个文件夹下哪些视频没被任何location收进去，手动选视频触发生成候选（见上"文件夹审查面板"）
- **地点**：地点列表+新建地点
- **分组**：地点多选+合并
- **一致率看板**：LLM vs 人工一致率统计

## 需要的后端小补丁（这次计划自己的前几个任务，不是另一个独立计划——执行者直接把它们当成Task 0做，不用等别的工作完成）

builder check（找了一个没看过这次对话的"假装不认识设计文档作者"的工程师来挑刺）发现这几块当时漏写了，现在补全：

1. `locations`表加`representative_video_sha256`（可空bytea，FK videos.sha256）——`apply_human_decision`回填`representative_frame_path`时一并回填这一列。详情/列表接口返回候选地点信息时，用这条video的`collect_lon`/`collect_lat`/`srt_height`跟当前视频算`distance_3d_meters`（复用`app/services/geo.py`现成函数），返回`gps_distance_meters`字段。
2. `GET /location-review/queue/{item_id}`等返回里，`screenshot_path`→`screenshot_paths`（数组，序列化层面包一层，不改数据库列）。
3. 加CORS中间件（FastAPI自带`CORSMiddleware`），允许前端开发/部署的源。
4. **（新增）地点/分组的只读列表接口**：`GET /location-review/locations`（返回id/city/site/representative_frame_path/location_group_id）、`GET /location-review/groups`（返回id/name/confirmed_at/成员location列表）——"地点管理"和"分组管理"这两个页面需要先看到现有地点/分组才能选，目前后端只有"新建"和"合并"两个写接口，没有"列出来看看"的读接口，这是真实缺口，不是风格问题。
5. **（新增）复核条目的返回里，把候选地点的身份信息内联进去**：`candidate_location_id`旁边直接带上`candidate_city`/`candidate_site`/`candidate_representative_frame_path`（如果已分组还可以带上`candidate_group_name`），不要求前端拿到一个裸的id后再单独查一次——核心复核面板需要显示"候选图是哪个地点"，不能只有一个数字id。
6. **（新增）队列列表接口里，每条item带上视频自身的识别信息**：`video_filename`（从`storage_path`取文件名，不需要完整路径）、`video_city`、`video_collected_at`——复核员扫一眼队列列表就要知道"这是哪条视频"，不能只看sha256。
7. **（新增，"文件夹审查"面板用）`GET /location-review/folder-audit?storage_path_prefix=...`**：给一个文件夹路径前缀，查`videos.storage_path LIKE prefix||'%'`的全部视频（不限城市/不重新解析site名字——2026-11-26跟用户确认过，不新增`videos`表的列，也不碰`scanner.py`，纯粹按路径前缀查已有数据），每条返回`video_sha256`/`storage_path`/`location_id`(可能为NULL)/`is_stable`/`collect_lon`/`collect_lat`，前端据此标出"这个文件夹里哪些视频没被收进任何location"，供人工判断是否该手动塞进复核队列。

**不新增的（决定不做，记录原因）**：
- 同一视频被多个候选"陪审"的item，人工决策其中一个之后，其它几个不在后端层面自动关闭——不改现有`apply_human_decision`的语义（这是已经上线验证过的代码，不想因为前端需要就回头改它的状态机）。改成前端处理：队列列表拿到每条item时，一并检查对应`video.location_confirmed`，已经锁定的视频，它名下其余`pending`的item在前端直接标成"已通过其它条目处理"灰显/可折叠，不需要用户点开才发现是废条目。
- 队列列表分页：现阶段这是几个白名单内部人员用的工具，复核条目量级是几十到几百条，**先不加真分页，后端一次性返回当前status筛选下的全部条目，前端自己做客户端分页/虚拟滚动**。真到量级起来需要游标分页再加，不在这次范围。
